Research date: **2026-10-26**. Planning only. Read [AGENTS.md](../AGENTS.md) and the [migration assessment](railway_migration_assessment.md); consulted current first-party Railway documentation/source and PostgreSQL/SQLite documentation. ## Finding: upload exists, but do not assume a stopped service works

Railway officially documents `railway volume files upload LOCAL_PATH REMOTE_PATH`, including files and directories. `--volume` belongs **before** `upload`, on the `files` group. This transfers an archive; no archive-extraction subcommand is documented. [CLI volume reference](https://docs.railway.com/cli/volume#manage-files)

There is a material conflict in first-party evidence:

- The [May 29 volume-browser announcement](https://railway.com/changelog/2026-05-29-cli-volumes) says transfers operate directly on volume storage without a running service container.
- The latest published CLI found was [v5.71.0, October 19](https://github.com/railwayapp/cli/releases/tag/v5.71.0), commit `b62467ef1b5303e3e340283ed96425dcf9612993`. Its `volume_file_target` requires an attached service and calls `ensure_service_has_active_deployment`; that helper rejects a service with no active deployment. This is released source, not just an unreleased branch. [Volume target resolution](https://github.com/railwayapp/cli/blob/b62467ef1b5303e3e340283ed96425dcf9612993/src/commands/volume.rs#L297), [active-deployment check](https://github.com/railwayapp/cli/blob/b62467ef1b5303e3e340283ed96425dcf9612993/src/controllers/project.rs#L296)

**Recommendation:** plan around a running, harmless importer deployment with the target volume attached. Barkd itself need never run during transfer/extraction. A truly container-free upload is not established by these conflicting sources; confirm with Railway or a disposable-volume rehearsal before depending on it.

## Proposed import without starting Barkd or creating a wallet

1. **Prepare an offline artifact.** After all source wallet activity has stopped, preserve the complete `/data/barkd` directory, including hidden files and any SQLite journal/WAL companions. Do not substitute a mnemonic import, a newly created wallet, or a copy of only the main SQLite file. SQLite documents corruption risks from copying during transactions and separating a database from its required journal/WAL. Retain the original offline artifact and its checksum. [SQLite backup/copy hazards](https://sqlite.org/howtocorrupt.html#_backup_or_restore_while_a_transaction_is_active)

2. **Deploy tools before the wallet image.** Create the intended private signet service initially with a reviewed tools-only `linux/amd64` image containing a shell, `tar`, `sha256sum`, and `sleep`, **without Barkd or any wallet initialization logic**. A long-running start command such as `sleep infinity` is suitable when the chosen image supports it. Attach the fresh persistent volume at `/data`; use one instance, disable Serverless and automatic image updates, and leave public networking and HTTP healthchecks unconfigured for this importer. Using the eventual service avoids volume detachment/reassignment. Railway mounts volumes at runtime, not during image builds. [Volume mounts](https://docs.railway.com/volumes#volume-availability), [image deployment/architecture](https://docs.railway.com/guides/private-container-registry)

3. **Upload through the official CLI.** After verifying the project, signet environment, and volume IDs, the documented command shape is:

   ```sh
   railway volume --project <PROJECT_ID> --environment <SIGNET_ENV_ID> \
     files --volume <VOLUME_ID> upload ./barkd-offline.tar /barkd-offline.tar
   ```

   Do not add `--overwrite` for the initial import. In the inspected CLI, volume-relative `/barkd-offline.tar` maps to `/data/barkd-offline.tar` when the mount is `/data`; `/` means the volume root. Confirm that mapping on harmless test data with the actual CLI version. [Upload arguments](https://docs.railway.com/cli/volume#options-for-files-upload), [path mapping implementation](https://github.com/railwayapp/cli/blob/b62467ef1b5303e3e340283ed96425dcf9612993/src/commands/volume/sftp.rs#L1022)

4. **Verify and extract in the importer, not in a pre-deploy hook.** Use `railway ssh` to run filesystem tools in the active importer container. Compare the uploaded archive checksum with the retained source checksum, inspect archive paths, and establish the extraction destination before writing. Reject unexpected absolute/traversal paths or escaping links; do not merge into an existing wallet directory. For an **uncompressed** archive already verified to contain one relative top-level `barkd/` directory, with `/data/barkd` absent, this is an illustrative extraction command:

   ```sh
   railway ssh --project <PROJECT_ID> --environment <SIGNET_ENV_ID> \
     --service <IMPORTER_SERVICE_ID> -- \
     tar -xpf /data/barkd-offline.tar -C /data
   ```

   Archive layout/compression and target ownership remain unknown; do not apply this example blindly or guess `--strip-components`, UID, or GID. Verify the resulting path is exactly `/data/barkd`, file completeness, and ownership/modes against the final image's actual Barkd user. Reserve capacity for both archive and extracted files. The importer performs file operations only; no wallet or SQLite process is needed. [Remote command execution](https://docs.railway.com/cli/ssh#run-a-single-command), [volume permissions](https://docs.railway.com/volumes#permissions)

5. **Keep activation separate.** Leave the importer running until the copied tree is approved for activation; never execute `barkd`, wallet `create`, or recovery commands to prepare the volume. Later, replace the tools source/start command with the exact tested Barkd **0.8.0** image and its normal entrypoint, preserving the same `/data` volume. Only activate after the source wallet remains stopped and the migration checks below pass. The local [Dockerfile](../fly/barkd.Dockerfile) and [entrypoint](../fly/barkd-entrypoint.sh) establish `/data/barkd` and the Barkd user. Railway's image Start Command overrides the image entrypoint, so an importer override must be deliberately cleared/replaced at activation. [Start-command semantics](https://docs.railway.com/deployments/start-command)

**Transport:** prefer CLI SFTP or native `scp`/`sftp` to the importer over an HTTP artifact server. Railway supports these clients with a registered SSH key; a private service can use its **service instance ID** as the SSH username, which differs from its service ID. For example, `scp ./barkd-offline.tar <SERVICE_INSTANCE_ID>@ssh.railway.com:/data/barkd-offline.tar` targets the active container's mounted volume. No public Barkd domain or TCP proxy is needed. [SSH/SFTP reference](https://docs.railway.com/cli/ssh#copy-files-with-scp-and-sftp)

If the CLI upload is unavailable, native SFTP to that tools container is the documented fallback. If an object-store download is operationally necessary, the proposed alternative is an authenticated private object, preferably additionally encrypted, fetched by the tools container using narrowly scoped, short-lived access. Never put the wallet archive in Git, a Docker image/build context, a public bucket, or an unauthenticated download URL. Do not log artifact URLs, decryption keys, or wallet contents. Exact download/decryption commands require the chosen store and tooling; none are asserted here.

## CLI distinctions that matter

- **`railway ssh`: remote container.** Executes a shell/command inside an already deployed service; it does not create a clean replacement process for a stopped wallet service. Choose the tools deployment explicitly. [SSH](https://docs.railway.com/cli/ssh)
- **`railway connect`: local database client.** Launches local `psql`/equivalent against a public TCP proxy, or an SSH tunnel when the database is private. `--ssh` forces tunneling; `--tunnel-only` opens a local tunnel for other tools and **prints credentials/connection details**, so keep that output out of transcripts/logs. It is neither a container shell nor a volume uploader. [Connect](https://docs.railway.com/cli/connect)
- **`railway run` / alias `railway local`: local execution with service variables injected.** They do not execute inside Railway or mount its volumes. `railway shell` also opens a local environment. Do not use either as a remote restore/import mechanism. [Run](https://docs.railway.com/cli/run), [shell](https://docs.railway.com/cli/shell)
- **Pre-deploy commands:** remote, private-network capable, but run in a separate container **without mounted volumes**; filesystem changes do not persist. They cannot unpack this wallet into its volume. Use the active importer or an importer start command instead. [Pre-deploy constraints](https://docs.railway.com/deployments/pre-deploy-command)

## Networking, deployment controls, and shutdown

- **API:** retain `0.0.0.0:3000`, explicitly set Railway `PORT=3000`, and route the public domain to port 3000. Configure `/health` as the deployment healthcheck. Railway uses `PORT` for healthchecks, expects a successful `2xx`, and does not continuously monitor this endpoint after activation. [Binding/target ports](https://docs.railway.com/networking/troubleshooting/application-failed-to-respond), [healthchecks](https://docs.railway.com/deployments/healthchecks)
- **Private Barkd:** keep API, Barkd, Postgres, and Redis in the same signet project/environment. Private DNS is `<service-name>.railway.internal`; use internal HTTP and the listening port. Environments created after **October 16, 2025** resolve both IPv4 and IPv6; legacy environments resolve IPv6 only. Consequently IPv4-only binding can work in a new environment but is insufficient in a legacy one. Verify client address selection and the actual listener; do not assume an `::` listener necessarily accepts IPv4 too. The existing Barkd image defaults to `BARKD_BIND_HOST=::`. [Private-network architecture/DNS](https://docs.railway.com/networking/private-networking/how-it-works), [library configuration](https://docs.railway.com/networking/private-networking/library-configuration)
- **Noah configuration blocker:** [config.rs](../server/src/config.rs) validates signet Barkd against `noah-barkd-signet.internal:3000`. A Railway hostname needs an intentional validation change preserving network separation before the API can use it. This research does not make that change.
- **Singleton:** Railway permits one volume per service and prohibits ordinary replicas with volumes; volume-bearing redeployments have downtime because deployments cannot simultaneously mount it. This does not prevent a second wallet copy running on Fly or in another service. Maintain one active wallet across providers. [Volume limitations](https://docs.railway.com/volumes/reference#caveats)
- **Control automation:** disable GitHub autodeploys if attached, leave Docker image auto updates disabled, and explicitly disable **Serverless** for the API and Barkd. Semver image auto updates can advance a pinned version tag. Fly's migration guide says its importer can enable Serverless from Fly autostop settings; inspect the result instead of assuming always-on behavior. Serverless changes take effect when a container is deployed. [GitHub controls](https://docs.railway.com/deployments/github-autodeploys), [image updates](https://docs.railway.com/deployments/image-auto-updates), [Fly import behavior](https://docs.railway.com/platform/migrate-from-fly), [Serverless](https://docs.railway.com/deployments/serverless)
- **Stopping and restarts:** deployment **Remove** stops the active deployment; **Abort** cancels an initializing/building deployment. Restart policy defaults to `On Failure`, maximum **10** restarts; choose deliberately for the importer. Disabling autodeploys does not prevent mandatory Railway host-maintenance/fault redeployments. [Deployment actions/lifecycle](https://docs.railway.com/deployments/reference), [restart policy](https://docs.railway.com/deployments/restart-policy)
- **Graceful stop:** Railway documents **SIGTERM followed by SIGKILL**, with **0 seconds default draining time**, and no alternative stop signals. Set `RAILWAY_DEPLOYMENT_DRAINING_SECONDS` (or `deploy.drainingSeconds`) explicitly; the existing Fly signet Barkd config allows **30 seconds**, a starting value to rehearse rather than proof of sufficiency. Overlap time is a separate control. Verify signal propagation and clean exit before the offline copy; do not assume Docker/Fly grace defaults carry over. [Lifecycle defaults](https://docs.railway.com/deployments/reference#singleton-deploys), [teardown controls](https://docs.railway.com/deployments/deployment-teardown), [Fly signet settings](../fly/signet.barkd.fly.toml)

## PostgreSQL logical migration and support boundary

Use a logical dump/restore into a fresh Railway Postgres database; do not place a Fly Postgres physical datadir in Railway's database volume. Railway documents custom-format dumps, local SSH-tunnel access, `pg_restore --no-owner --exit-on-error`, and restore drills. Keep the API and all background writers stopped through the final export/restore; a consistent dump alone does not capture subsequent source writes. [Railway backup/restore guide](https://docs.railway.com/guides/postgres-backups-restores)

- **Version/format checks first:** source server major, dump-producing client major, archive format, destination major, required extensions, and role/ACL dependencies are unknown. Prefer the same server major for a migration rehearsal; treat an upgrade separately. `pg_dump` must not be older than the source server major. Loading its output into an older server than the dump client is not guaranteed. Use a compatible restore client, ordinarily from the same tool release that produced the dump, and rehearse. `pg_dump` covers one database, not cluster-wide roles/tablespaces. [PostgreSQL `pg_dump`](https://www.postgresql.org/docs/current/app-pgdump.html)
- **Correct a Railway example:** the Fly migration guide dumps with `-Fc` but restores with `-F t`. Those formats conflict. For an existing custom archive, let `pg_restore` autodetect or specify `--format=custom`; plain SQL goes through `psql`, not `pg_restore`. Consider `--no-owner --no-acl` when intentionally mapping Fly ownership/privileges to the target role, and `--exit-on-error` so restoration does not continue silently after errors. Do not blindly recreate provider-specific roles. [Fly example](https://docs.railway.com/platform/migrate-from-fly#3-database-migration), [PostgreSQL restore options](https://www.postgresql.org/docs/current/app-pgrestore.html)
- **Managed does not mean unrestricted support:** stock Postgres starts as one maintained node; HA and backups/PITR require explicit enablement. Railway handles provisioning/storage/networking and image security patches; users own schema/data and choose protection, upgrades, and sizing. Custom image/start/template-variable changes, manual volume/container edits, and SQL changes to roles/settings/extensions can move the database outside managed database support, while platform support remains. A logical schema/data restore avoids manually replacing the database volume, but its configuration SQL still needs review. [Postgres template](https://docs.railway.com/databases/postgresql), [responsibility/support scope](https://github.com/railwayapp/docs/blob/4bc46bc0ba1b27d50c5ef0393132753982b31112/content/docs/databases.md#database-support-scope)

## DNS cutover and remaining gates

For a hostname Noah controls, add it as an API custom domain and use the dashboard's exact **CNAME and ownership TXT records**; both are required. Railway documents a `404` when the TXT verification is missing. Inventory existing Fly routing records before replacing them; apex domains require ALIAS/CNAME flattening support. Railway provisions TLS automatically; issuance is expected within an hour, while DNS propagation can take up to 72 hours. Do not promise an instantaneous or zero-downtime certificate/DNS change. [Custom-domain records](https://docs.railway.com/networking/domains/working-with-domains#custom-domains), [apex/TLS limits](https://docs.railway.com/networking/public-networking/specs-and-limits)

Proposed sequencing: lower DNS TTL in advance, test the API on its Railway domain, stop Fly API/background writers and Barkd, take final offline artifacts, restore/verify, activate only the Railway wallet/API, then switch the controlled public hostname and verify TLS plus representative requests. Keep the old endpoint from accepting writes while caches expire. A DNS reversal after Railway has accepted writes is **not** a data rollback; establish a reconciliation decision before reopening Fly. Retain source artifacts and infrastructure until acceptance. Redis coordination/auth-state handling remains required by the existing assessment and is outside this focused import research.

Before execution, resolve: the CLI/changelog conflict and SSH prerequisites on a disposable volume; archive layout/checksum/ownership/capacity; actual PostgreSQL versions/extensions/ACLs and restore results; Barkd private address-family behavior, shutdown duration, and unchanged wallet identity/state after import; the hostname-validation change; and DNS/TLS readiness. No live inventory, credential reads, transfer, extraction, wallet startup, or database restore was performed to validate those items.
