# Railway migration assessment

Research date: **2026-10-23**. Current first-party Railway documentation and local source; no infrastructure or code changes, credential reads, deployment tests, or restore tests. Live inventory and cost figures below were supplied by the parent investigator, not independently collected here.

## Recommendation

**Railway is a credible consolidation candidate; prove the complete signet deployment first, then decide mainnet from measured total cost and recovery exercises.** Its current product includes managed Postgres and Redis HA with automatic failover. Default single-node templates do not include that redundancy. For mainnet, prioritize Postgres HA, enabled PITR, independent logical exports, and a tested Barkd recovery procedure over maximum savings. Use the same deployment conventions in isolated signet/mainnet environments, with explicitly documented differences in sizing and protection. Metabase can be removed or migrated last.

This is not evidence that Railway is inherently unreliable, nor that changing hosts alone fixes signet. Demonstrate improved uptime and successful background jobs on signet before moving mainnet data. HA, backups, operational ownership, and contractual uptime are separate properties.

## Managed responsibility and HA

- **Default Postgres and Redis are single nodes.** Railway maintains/runs them; HA is an explicit conversion, and backups/PITR must be enabled. Calling every Railway database “unmanaged” or claiming automatic failover is unavailable would be incorrect. [Postgres](https://docs.railway.com/databases/postgresql), [Redis](https://docs.railway.com/databases/redis)
- **Responsibility boundary:** Railway handles provisioning, storage, networking, and database-image security patches. Users enable backups, PITR, HA, and pooling, initiate major upgrades, resize disks, and own schema/data. Support covers stock templates and Railway's dashboard/CLI flows. Custom image/start-command/template-variable changes, manual volume or cluster-member changes, container edits, and database configuration through SQL (including roles/settings/extensions) can put the database outside managed support; platform support remains. Review this unusually specific scope against Noah's required configuration. [Responsibility and support scope](https://docs.railway.com/databases#what-railway-manages)
- **Postgres HA:** Patroni, etcd, and HAProxy provide automatic promotion and routing; existing connections drop and clients must reconnect. Conversion defaults add **2 replicas, 3 etcd nodes, 3 proxies**, making **9 components including the original primary**. Supported official images/major tags are required; custom start commands block conversion. Do not interpret this as a documented zero-data-loss or regional-disaster guarantee. [HA architecture and defaults](https://docs.railway.com/databases/postgresql-ha). Generally available since [March 27, 2026](https://railway.com/changelog/2026-03-27-cdn).
- **Redis HA:** Sentinel runs with each Redis node; HAProxy routes to the elected primary. Defaults add **2 replicas and 2 proxies**, making **5 components including the primary**. Requires supported versioned images and no custom start command; failover drops active connections. The docs do not establish zero acknowledged-write loss. [Redis HA](https://docs.railway.com/databases/redis-ha), [August 2026 release](https://railway.com/changelog/2026-08-20-railway-anon).
- **HA costs actual additional resources.** Include every data replica, consensus node, proxy, and associated volume in the estimate, plus optional PgBouncer. Railway describes HA as billed through added replicas; it is not bundled redundancy in a single-node quote. Reverting HA retains detached replica/consensus volumes and their storage charges until cleaned up. [Billing model](https://docs.railway.com/platform/compare-to-render#databases), [Postgres retained volumes](https://docs.railway.com/databases/postgresql-ha#reverting-to-standalone), [Redis retained volumes](https://docs.railway.com/databases/redis-ha#reverting-to-standalone)

## Recovery and deployment limits

- **Volume backups:** manual or scheduled incremental copy-on-write snapshots. Daily retention is **6 days**, weekly **27 days**, monthly **89 days**; multiple schedules can coexist. Manual backups have a documented **50%-of-volume-capacity limit**. Restore is restricted to the same project/environment and redeploys onto a restored volume; the previous volume remains detached. Newer snapshots remain on that previous volume. **Wiping a volume deletes its backups.** The backup reference is more precise than the Postgres guide's rounded “month/three months” and differs from that guide's statement that newer snapshots are removed; use the current reference and verify behavior in a rehearsal. [Backup reference](https://docs.railway.com/volumes/backups), [Postgres guide](https://docs.railway.com/guides/postgres-backups-restores)
- **Postgres PITR:** available for single-node and HA, enabled explicitly. pgBackRest archives WAL to a Railway bucket, with weekly full/daily differential backups and **last 4 fulls retained, roughly 4 weeks**. Async uploads mean this is not a zero-RPO promise; a prolonged bucket outage can fill the **5 GiB archive queue**, drop WAL, and truncate recovery coverage. Restore creates a new single-node sibling; manual cutover, HA conversion, and re-enabling PITR on that fork are separate steps. Coverage starts after the first base backup. Archive storage and upload egress are billed. No native Redis PITR is documented here. [PITR behavior and limits](https://docs.railway.com/volumes/point-in-time-recovery)
- **Independent exports:** Railway's Postgres guide recommends snapshots, PITR, and logical dumps together. Retain encrypted exports outside the service's volume/deletion boundary and test recovery; HA does not undo accidental data changes. [Production backup guidance](https://docs.railway.com/guides/postgres-backups-restores)
- **Upgrades:** Railway provides a preflighted Postgres major-upgrade flow with before/after backups and revert. The database stops, typically for minutes; on HA, failover stays paused while replicas rebuild. Revert discards post-upgrade writes. Directly changing the image's major tag does not migrate data. Do not assume rolling, uninterrupted upgrades. [Major upgrades](https://docs.railway.com/databases/postgresql-major-upgrade)
- **Volume services:** one volume per service; ordinary service replicas cannot use volumes. Redeployments have downtime even with healthchecks because deployments cannot share the mounted volume. This does not contradict database HA: Railway builds a cluster from separate services/volumes. Live enlargement is supported, shrinking is not; a full disk can require an offline resize/restart. [Volume limitations](https://docs.railway.com/volumes/reference#caveats)
- **Targets versus SLA:** pricing lists **99.9% Hobby / 99.99% Pro / 99.999% Enterprise availability targets**. These are not a default contractual database SLA; current database docs say no published uptime SLA and direct customers to sales for one. Verify any negotiated scope instead of treating the Pro target as guaranteed database availability. [Pricing](https://railway.com/pricing), [Production guidance](https://docs.railway.com/platform/use-cases#databases)

## Noah-specific implications

**Redis is stateful authentication and job-related coordination, not disposable cache.** [K1Store](../server/src/cache/k1_store.rs) issues expiring challenges and atomically consumes them with `GETDEL`; [InvoiceStore](../server/src/cache/invoice_store.rs) holds 60-second invoice responses; [EmailVerificationStore](../server/src/cache/email_verification_store.rs) holds 10-minute verification state; [MaintenanceStore](../server/src/cache/maintenance_store.rs) persists round timestamps/counters without TTL. Redis failure also blocks the startup connectivity check in [main.rs](../server/src/main.rs). Lost state interrupts these flows; restoring an older snapshot could resurrect an unexpired consumed challenge, so do not blindly restore stale auth state. Define a controlled reset/reconciliation policy.

The [notification coordinator](../server/src/notification_coordinator.rs) uses Postgres for notification tracking and pending job reports, while [push dispatch](../server/src/push.rs) issues per-dispatch K1s through Redis. Therefore Redis is part of the coordination/auth path, but it is inaccurate to claim the entire job ledger or notification-spacing state lives there. Keep server/Redis cutover coordinated; test challenge consumption, invoice exchange, verification, maintenance, and background-job reports after a restart/failover.

**Barkd should remain a private singleton per network.** Railway provides encrypted WireGuard private networking, service DNS, and isolated networks per environment. Place each API with its own Barkd/database/Redis in the appropriate environment and use private variable references; no public Barkd endpoint is required. [Private networking](https://docs.railway.com/networking/private-networking). Noah currently pins mainnet/signet Fly `.internal` hosts and port 3000 in [config.rs](../server/src/config.rs); migration needs a small validation change preserving network separation, not just new environment values.

The existing [Barkd container](../fly/barkd.Dockerfile) stores `/data/barkd`; [mainnet configuration](../fly/mainnet.barkd.fly.toml) uses a private singleton and requests 30 retained Fly snapshots. Mount the complete datadir persistently on Railway and explicitly configure backups. Generic volume snapshots cover volume contents, but the reviewed docs do **not** establish Barkd-specific application consistency, safe wallet rollback, cross-region recovery, or automatic wallet failover. Rehearse a stopped/quiesced signet wallet backup and isolated restore; verify wallet state and safe resumption with Bark's own recovery requirements. Never run two active copies of one wallet. Mainnet cutover needs one active writer, verified backup, reconciliation, and rollback boundaries that avoid two diverging wallet histories.

## Cost context supplied by parent

- Current Redis is **two Upstash pay-as-you-go services billed through Fly**, `noah-signet-redis` and `noah-mainnet-redis`; it is not two Redis VMs to subtract from a compute bill.
- Known Fly baseline: **$115.53 mainnet + $6.70 signet API + $3.84 signet Barkd/disk + $4.34 legacy signet Postgres/IP = $130.41/month**, before Redis, managed-Postgres storage, snapshots, network, taxes/credits. Signet API uses free ingress IPs.
- Read-only VM memory snapshots (`MemTotal − MemAvailable`): mainnet API **0.254 GiB**, signet API **0.174**, mainnet Barkd **0.070**, signet Barkd **0.069**, Metabase **1.472**; combined **2.040 GiB**. These omit Postgres/Redis and measure neither average process consumption nor Railway-billable RAM. Metabase dominates this particular snapshot and is unimportant to retain.
- Railway rates supplied by parent: RAM **$10/GB-month**, CPU **$20/vCPU-month**, volumes **$0.15/GB-month**, egress **$0.05/GB**. Pro's **$20 monthly minimum includes $20 usage**, so do not add another $20 to usage exceeding that amount. [Published rates](https://docs.railway.com/pricing/plans)
- **Illustration only:** average **6 GB RAM across all components**, **0.25 vCPU**, **40 GB volumes** gives **$60 + $5 + $6 = $71/month before backups and egress**. This is not a predicted deployment bill. Include both environments' Postgres/Redis HA components, backup/PITR storage and uploads, migration overlap, and any retained detached volumes before concluding savings.

**Decision gate:** demonstrate signet restart/failover behavior and restore recovery, measure the complete steady-state resource bill, and compare it with the complete Fly bill. Move mainnet only when those results justify the change without reducing its data protection; retain Fly mainnet meanwhile if safe Railway redundancy/recovery erases the savings.
