## Decisions to settle before migrating funded wallets

- **M0 prerequisite: preserve identity and data on upgrade.** Keep bundle/package variants, secure-store identities, MMKV root/id, Bark wallet directories and extension IDs. Import recurring policies and execution markers before enabling any scheduler. Do not let startup mistake moved-but-not-yet-imported data for a fresh install and clear credentials. Wallet seed alone does not restore Ark protocol state.
- **Keep one wallet owner per installed app.** Screens, push, recurring executor, backup snapshotting, restore/config reload and iOS App Intents can all touch the same native wallet. Existing JS job flags and service-local locks are not a complete global mutex. A native coordinator must define safe load/close/replace and operation concurrency while permitting long-lived receive subscriptions. Preserve safety semantics; do not reproduce weak JS synchronization just to match structure.
- **Retain the native Ark core.** The rewrite replaces React UI/orchestration and Nitro forwarding; it need not reimplement Bitcoin signing, Bark protocols or the wallet DB in Swift/Kotlin. Existing Objective-C++/JNI façades are starting points, with source/test parity required at their boundaries.
- **Treat tests as contract candidates, not proof of current coverage.** Port money/parsing/receive/schedule/accounting/exit cases into native tests; add real upgrade/storage/backup/background tests. This research enumerates existing specs but does not claim the whole suite passes. The translation extraction command was specifically attempted and fails on the installed CLI, detailed below.

Notable corrections to initial assumptions: `transaction-storage` stores auto-boarding preferences, not transaction metadata; receive requests are ephemeral; recurring policies are not backed up; `serializedSync.ts` serializes server schedule replacement, not all wallet synchronization; HTTP has no demonstrated custom certificate/proxy requirement; JWT auth is already live with a 72-hour default TTL; `bitcoin:`/`lightning:` parsing does not establish OS deep-link support.

Distinguish intended safety guarantees from existing implementation limitations: `lib/sync.ts` checks initialized/loaded but does not itself check suspension/background ownership; `useBackgroundJobCoordination.ts` proceeds after a 10-second wait and is not a mutex; `lib/tasks.ts` checks load errors without consistently treating an OK/false suspended-wallet result as a stop. These are static observations, not runtime-reproduced bugs. A native coordinator should enforce lifecycle/ownership explicitly rather than assume current JavaScript already guarantees exclusion on every path.

### Launch / onboarding / permission / security gates

1. `AppNavigation` starts with a wallet-check loading screen; Android also waits for tab icons. If persisted `isInitialized` is already true, wallet existence check is bypassed. Otherwise `getMnemonic()` is checked: mnemonic + wallet data calls `finishOnboarding`; mnemonic without data clears stale iOS Keychain and resets wallet/server/transaction stores. This handles Keychain surviving uninstall (`Navigators.tsx:535–571`).
2. Uninitialized users see Onboarding. Create → beta-risk acceptance → `useCreateWallet` → seed → email. Declining beta returns. Restore bypasses beta/seed display and calls `useRestoreWallet`, showing staged backup restore progress.
3. Email is optional. Registration happens before onboarding email UI unless already registered; a registration error returns back. Email success/skip → UnifiedPush on real non-GMS Android; otherwise battery screen if battery optimization applies; otherwise Lightning address. UnifiedPush → battery screen; battery skips itself if inapplicable and replaces with Lightning address. Lightning save/skip finishes onboarding; registration has already allocated an address, so skip retains it with NIP-05 disabled. Sources: `EmailVerificationScreen.tsx:61–96`, `UnifiedPushScreen.tsx:96–109`, `BatteryOptimizationScreen.tsx:48–73`, `LightningAddressScreen.tsx:43–86`.
4. For initialized wallets, push permissions are checked on initialization and every foreground transition. A **resolved DENIED status on a physical device** replaces the whole navigation with `PushNotificationsRequiredScreen` (no skip). Undetermined/checking/error does not itself block rendering; simulators unsupported by push bypass this gate. Request, retry status, and OS settings actions exist. Do not turn this into an unconditional permission prompt on every launch (`Navigators.tsx:573–679`).
5. Next comes the one-time Android battery-optimization gate, if initialized, prompt not previously seen, and native optimization says enabled. Continue/skip marks persisted `hasSeenBatteryOptimizationPrompt`. Recheck on foreground after visiting OS settings (`Navigators.tsx:647–689`, `lib/batteryOptimization.ts`).
6. `WalletLoader` loads actual native wallet only after background-job coordination allows it; reconciles persisted loaded state with actual native state; avoids duplicate loads; skips suspended wallets; best-effort closes on unmount. Spinner blocks children while loading absent error/suspension. It then wraps children in `BiometricGate` (`components/WalletLoader.tsx`).
7. BiometricGate authenticates on initial access if enabled; no content flash before initial check. After first successful unlock it **keeps services/navigation mounted** while overlaying a lock view that blocks touches. AppState handling ignores changes caused by its own biometric prompt to avoid recursive prompting. Code specifically handles direct active→background lock and background→active authentication. Disabling biometrics unlocks immediately. Authentication failure offers retry. Native implementation should preserve the intended background lock without relying on RN-specific transition behavior (`components/BiometricGate.tsx:31–164`).
8. Only then mount `AppServices` + tabs. Home has suspended-wallet UI that still links to Settings for resume; wallet/load errors and server/background/update/backup/email/autoboard/pending-round status banners are separate from launch gates. A minimum-version banner is present, not a new navigator route (`HomeScreen.tsx`).

### Deep links and URL schemes: actual behavior versus requested assumptions

- `client/app.config.ts:109–113` declares iOS mainnet bundle/scheme `com.noahwallet.mainnet`. Actual committed `client/ios/Noah/Info.plist:31–46` registers `$(APP_SCHEME)` and `exp+noahs-ark-wallet`; `client/ios/Config/{mainnet,regtest,signet}.xcconfig` set `com.noahwallet.mainnet`, `.regtest`, `.signet` respectively. The iOS prebuild fix preserves this (`client/plugins/withNoahIosPrebuildFix.js`). AppDelegate forwards URL opens/universal-link activity to RCTLinkingManager (`client/ios/Noah/AppDelegate.swift:30–48`); SceneDelegate subclasses ExpoAppSceneDelegate.
- `client/android/app/src/main/AndroidManifest.xml:36–46` has MAIN/LAUNCHER plus only the `exp+noahs-ark-wallet` VIEW/BROWSABLE scheme. MainActivity is `singleTask`. The HTTPS entry at `:25–29` is an outbound package-visibility **query**, not an inbound intent filter. No `bitcoin`, `lightning`, `lnurl` or `com.noahwallet.*` payment intent filter was found in committed app manifests.
- **No `NavigationContainer linking` config, `Linking.getInitialURL`, URL listener or `useURL` consumer was found in app source.** Registered custom launch schemes should not be described as implemented payment deep links. Adding OS-level payment handlers in the native rewrite is new behavior, unless another build-time source is deliberately added.
- `bitcoin:` (case insensitive) is BIP-321 input parsing; `lightning:` is stripped for Lightning invoices/offers/addresses; Bitcoin/Ark network mismatch is rejected. Raw Ark address, Bitcoin address, BOLT11, BOLT12 and Lightning address inputs are supported via QR/paste/text (`lib/sendUtils.ts`, `hooks/useSendScreen.ts`). Destination type named `lnurl` means validated `name@domain` Lightning address in this parser; a generic `lnurl:` or encoded `LNURL1…` inbound scheme handler was **not** found. Preserve proven parsing contracts rather than inferring support from the type name.
- Outbound links include mempool explorer, Telegram/GitHub, app settings, BTC Map merchant/website/phone/social links, Apple Maps `http://maps.apple.com` or Android `geo:`. iOS query schemes are WhatsApp/Telegram/Signal. Widget/App Intent foregrounding is separate from screen routing; native App Intents already implement authenticated balance/address/invoice actions (`docs/app_intents.md`, `client/ios/SharedAppIntents/NoahAppIntents.swift`).

## Core logic, background coordination, persisted state and test inventory

Read-only source inspection on 2026-10-19. Paths below are relative to the repository root `/Users/niteshchowdharybalusu/Documents/noah`. Source code takes precedence over older design docs. `P` = deterministic/pure domain or presentation logic, `E` = filesystem/network/native/notification side effects, `R` = React state/query adapter; mixed labels mean both. “Exact” means preserve externally observable/security/accounting semantics, not necessarily port JS structure. Hook/query/render wrappers can generally be replaced by native observable models and structured concurrency.

### Behaviors that require native parity

- **Wallet creation and identity** (`client/src/lib/walletApi.ts:80`, `:146`, `:194`; `client/tests/integration/walletCreation.test.js`): coalesce overlapping creation; resume an existing seed + data pair without generating a new seed; reject incomplete seed/data and suspended wallets; delete only a failed *fresh* attempt. Keep variant-specific Bark data directories and keychain identity. Startup checks for seed without wallet data can clear stale keychain after iOS reinstall: changing the native data path before migration is unsafe.
- **Money representations** (`client/src/lib/bitcoinAmount.ts`, `fiatCurrency.ts`, `utils.ts`, `balanceUtils.ts`): amounts are sats; BIP177 renders `₿` + NBSP + localized integer, not BTC decimals. BTC URI amount divides by 100,000,000; fiat-to-sat rounds to nearest integer; JPY/KRW have zero display decimals. Typed number formatting preserves entered fractional digits and trailing decimal separator; receive currency toggles pin canonical sats to avoid rounding drift. Total balances include pending buckets, while send eligibility uses spendable/confirmed funding appropriate to rail.
- **Send interpretation** (`client/src/lib/sendUtils.ts`, `sendFlow.ts`, `client/src/hooks/useSendScreen.ts`): Bitcoin BIP321 URI can contain onchain/Ark/BOLT11/BOLT12; retain valid alternatives and prefer eligible Ark → Lightning → onchain, BOLT11 before offer on Lightning. Preserve mainnet vs signet/testnet/regtest network rules, case-insensitive `lightning:`, normalized Lightning addresses, checksum-less BOLT12 offer continuation `+` handling/uniform case, amountless/zero request editable, fixed invoice amount locked and sub-sat invoice rejection. BOLT12 structural checks defer authoritative semantic/TLV validation to Bark. MAX only accepts an onchain method, explicitly chooses onchain vs offchain source, does not sum the balances. Notes only when LNURL advertises comments; a note disables Ark-direct LN-address optimization. `constants.ts` has the actual LN-address regex, onion rejection and network rules; do not silently replace with a broader parser without parity decisions.
- **Receive identity and completion** (`client/src/lib/receiveRequest.ts`; `client/src/hooks/useReceiveRequest.ts`): amountless BIP321 includes fresh Ark + onchain addresses but no invoice; positive safe-integer amount adds Lightning invoice and exact BTC URI amount. Generation/session IDs reject late results after navigation or amount edits. Completion only matches the active Ark address or invoice payment hash, accepts successful receive movements once, invalidates balance/history, and cleans subscriptions; failed/canceled Lightning clears request and alerts. Subscription failures retry after 1s; release is deferred to avoid blocking native callback execution. **Receive requests are not persisted**.
- **Auto-board is an explicit confirmation flow** (`client/src/lib/autoBoarding.ts`; `client/src/components/AutoBoardingService.tsx`): confirmed onchain balance must cover net minimum `max(Ark minimum,20,000 sats)` + estimated regular onchain fee + **5,000-sat reserve**. Gross minimum iterates Ark fee estimation up to five times; final fee must still meet net minimum. Show gross/Ark fee/onchain fee/remaining/net before sending. Confirm records attempted flag; cancel disables auto-board; dismissal records attempted; enabling resets attempted. Do not turn this into silent sweeping.
- **History is accounting, not just UI** (`client/src/lib/transactionHistory.ts`, `barkMovement.ts`, `repeatPayment.ts`; `client/src/hooks/useTransactions.ts`): merge board movement with matching BDK tx so transfer is not duplicated; board internal transfers are neutral; offboards remain outgoing; canceled exits neutral; preserve signed intended/effective/fee values. Skip failed ordinary movements but retain board history; unknown onchain times are not fabricated current times. Repeat-payment metadata is `noah.repeat_payment` version 1 inside **Bark movement metadata**, including recipient/comment/original fiat-or-sat amount and currency; fiat prefill only when current currency still matches. It is **not** in transaction-storage.
- **Exit reads must never broadcast** (`client/src/hooks/useUnilateralExit.ts:83`, `client/src/lib/exitApi.ts:14`, `exitFeeEstimate.ts`, `exitTimeline.ts`): Bark `syncExit()` permits progression, so overview and estimates explicitly do not call it. Start/claim/progress require user actions. Eligible exit VTXO = Spendable and >= **330 sats**. Quote full selection as a set; pin wallet ID, sorted VTXO set, amount, scope, destination and revision; debounce 350ms, expire/requote at **30s**, invalidate on focus/background/wallet/background-job change, recheck spendability before start. Broadcast funding is separate from proceeds: recovered amount = max(0, value − claim fee), not value − total fee. Claim = drain PSBT → extract → broadcast → best-effort sync; post-broadcast sync failure must not present already-sent claim as failed. Cancellation only until final exit tx is broadcast; timeline includes canceled as terminal.
- **Recurring policy is device-only** (`client/src/lib/recurringSchedule.ts`, `recurringPayments.ts`; `docs/recurring_payments.md`): server gets only opaque ID + due time, never recipient/amount/policy; push is a wake-up, not payment authorization. Max 50 schedules; local calendar arithmetic preserves wall-clock time through DST, clamps month-end without drift; weekly/monthly interval up to 12, custom days up to 365; start permits 5-min clock skew. Pay at most latest due occurrence, record skipped older occurrences, never catch up in bulk. Persist in-flight before send; older than 10 min → needs_attention; never auto-retry an ambiguous send. Retry preflight failures 15 min doubling to 6h; manual trigger bypasses backoff. Re-read active schedule after async preflight and immediately before native submission, without intervening await; pause/cancel wins, completed result never recreates removed schedule or reactivates paused one. Resume skips overdue occurrences; last 24 run entries kept. Single shared executor promise prevents same-runtime overlap. iOS has no recurring periodic background task; real Android without GMS disables recurring because native UnifiedPush path does not execute it. Schedules are **not in encrypted wallet backups**.

## Scope and migration recommendation

`client/nitromodules/noah-tools/src/NoahTools.nitro.ts` exports **34 methods**. `src/index.tsx` forwards them through a single Nitro hybrid object. Delete this JS/Nitro forwarding layer as each caller becomes native; retain the native behavior as ordinary Swift/Kotlin services. Generated `nitrogen/` bindings, `HybridNoahToolsSpec` inheritance, `Promise` bridges, and React Native context access become unnecessary. Do not confuse removing this bridge with rewriting Ark itself: native wallet calls currently still go through the separate `react-native-nitro-ark` Rust/C++/JNI integration.

Primary implementation paths:

- iOS: `client/nitromodules/noah-tools/ios/NoahTools.swift`, `NoahToolsBackup.swift`, `NoahToolsHttp.swift`, `NoahToolsLogging.swift`, `NoahToolsWidget.swift`, `Extensions/NoahTools+Audio.swift`.
- Android: `client/nitromodules/noah-tools/android/src/main/java/com/margelo/nitro/noahtools/NoahTools.kt`, `NoahToolsBackup.kt`, `NoahToolsHttp.kt`, `NoahToolsLogging.kt`, `NoahPushService.kt`, `audio/NoahToolsAudio.kt`.
- Existing non-JS iOS wallet façade: `client/ios/Noah/NoahArkBridge.{h,mm}` and `NoahNativeWalletService.swift`.

Suggested milestone placement: M1 variant/configuration, secure-storage compatibility and wallet façade; receive/send milestones include HTTP/auth/native push; backup milestone includes encryption and transactional install; settings milestone includes logs, audio, battery exemption and UnifiedPush selection; widgets/intents milestone ports existing native targets and handlers with little UI redesign. Shared wallet ownership must be settled before mixing new native screens with old JS ones.

## HTTP rationale and exact boundaries

`NoahToolsHttp.swift` is a shared **ephemeral** `URLSession`, resource timeout 60 seconds, `waitsForConnectivity=false`, cellular/expensive/constrained networks permitted. POST/GET use per-request timeouts (JS wrapper defaults 30 sec), async data requests and textual response conversion. Upload/download default to 60 sec. There is **no background URLSession identifier**, OS-resumable upload scheduling, delegate certificate override, certificate pinning, trust bypass, custom proxy or Tor configuration in this module.

`NoahToolsHttp.kt` explicitly calls its client a “background requests” client, uses OkHttp connect/read/write timeout 30 seconds, disables connection-failure retry, creates derived clients for custom timeouts, and executes on Nitro asynchronous work. The service reuses it without JS. No custom TLS/proxy logic appears here either. Thus evidence supports native networking usable by background/native code and file transfers without moving entire backup payloads through JS; it does **not** establish a certificate/proxy workaround as its historical motivation. Source/history checked did not provide a stronger rationale. Remove the Nitro adapter, retain normal URLSession/OkHttp.

Platform configuration is separate: `client/ios/Noah/Info.plist` has arbitrary loads false and local networking true; `client/android/app/src/main/AndroidManifest.xml` allows cleartext traffic, as does debug manifest. Preserve regtest reachability deliberately. The anti-proxy/redirect/DNS-pinning discussion in `docs/unified_push.md` describes **server outbound delivery**, not this client HTTP module.

## Backup compatibility is a data contract

`NoahToolsBackup.swift` / `.kt` agree on encrypted layout: one-byte version (1 legacy, 2 snapshot), 16-byte random salt, 12-byte GCM IV, ciphertext, 16-byte tag. Key derivation is PBKDF2-HMAC-SHA256 with **600,000 iterations**, 32-byte/256-bit key and mnemonic password. Preserve ZIP root layout and encryption exactly for existing cloud/local backups. Swift uses CommonCrypto/CryptoKit/ZIPFoundation; Kotlin uses Java crypto/ZIP. Implementations currently read ZIP/encrypted data into memory; streaming encryption is an optional optimization, not a contract change.

v2 ZIP root is `manifest.json` + `db.sqlite`; legacy root is `backup_staging/noah-data-<variant>`. Keep snapshot validation and wallet identity/network checks from `client/src/lib/backupService.ts`; the bridge only transports manifest JSON. Snapshot install/finalize/rollback are intentionally separate to restore the original wallet if loading the candidate fails. Legacy restore is destructive internally and must remain protected by caller orchestration. `docs/backups.md` requires `/v0/backup/v2/*` for new backups, retaining legacy API only for compatibility/restore; do not reintroduce legacy whole-directory backup creation.

## Android UnifiedPush service: complete native workflow

`client/nitromodules/noah-tools/android/src/main/java/com/margelo/nitro/noahtools/NoahPushService.kt` is **808 lines**. Manifest registers unexported `PushService` with `org.unifiedpush.android.connector.PUSH_EVENT`; it does **not** declare a separate `android:process`, despite documentation’s loose “background process” wording. It does not require the JS event loop. Initialization loads Nitro core/noah-tools libraries; reflection locates `com.margelo.nitro.nitroark.NitroArkNative.INSTANCE` and invokes JNI methods.

1. **Configuration/cold start.** Derive mainnet/signet/regtest from package suffix. Read bundled `noah_bark_config.json`; AndroidBarkConfig gets Ark URL, refresh threshold, fee fallback, Esplora override/default, optional bitcoind credentials, claim delta, exit margin and round confirmations. Read mnemonic and Esplora override from encrypted `noah_native_secrets`; wallet path is `filesDir/noah-data-<variant>`. `isWalletLoaded`/`loadWallet` is protected by a service-local `walletLock`. It is a load lock, not a critical section for every operation. Some cold-load helpers log and return on missing data; later actions can still fail, so migration should use a definite load-success result.
2. **Authentication.** A service-local `authLock` serializes token acquisition. JNI `peekKeyPair(0)` supplies current public key. Cache `server_auth_<variant>_token`, `_expires_at`, `_public_key` in encrypted preferences. Reuse only if key matches and expiry is over five minutes away. Otherwise GET `/v0/getk1`, JNI `signMessage(k1,0)`, POST `/v0/auth/login` `{key,sig,k1}`, cache `access_token` with `expires_in_seconds`. Callbacks use bearer token. HTTP 401 clears cache, logs in again and retries once. `notification_k1` is correlation, never bearer authentication.
3. **maintenance.** Ensure wallet loaded, invoke `maintenanceDelegated()`, then authenticated POST `/v0/report_job_status` with `report_type="maintenance"`, success/failure, optional error_message, notification_k1. Skip report without k1. If report responds 404, retry after 250 ms, 1 sec and 2 sec (server persistence race). No generic retry for other statuses. It does not run JS sync, update JS backup dirty state, or write widget cache.
4. **lightning_invoice_request.** Read `amount` in msat; integer-divide by 1000 to sats; obtain `transaction_id`. Call `bolt11Invoice(sats)` (this JNI overload has no supplied description), extract invoice and payment hash, POST `/v0/lnurlp/submit_invoice` `{invoice,transaction_id}` with JWT. Abort claim thread if submission fails. On a separate Thread, invoke **`tryClaimLightningReceive(hash, false, null)`**, up to 30 attempts, sleeping 800 ms between failed attempts. Only a successful return produces local notification; all failed attempts produce no receipt notification. Channel `noah-push-default`, importance HIGH, fixed English “Lightning Payment Received! ⚡” / “You received <sats> sats”, auto-cancel and generated notification ID. No explicit click intent in this notification. Thread has no foreground service/work-manager durability guarantee.
5. **heartbeat.** Require server endpoint and `notification_id`; ensure wallet loaded; authenticated POST `/v0/heartbeat_response` `{notification_id}`. Log failure/success.
6. **Other types.** Only these three cases exist. `offboarding`, `backup_trigger`, recurring-payment types etc. are not handled; unknown type only logs warning. Maintain feature parity from the JS paths rather than assuming native UnifiedPush covers them.
7. **Registration callbacks.** `onNewEndpoint` writes `noah_unified_push/endpoint_<instance>` and legacy `endpoint`; JS later registers endpoint with server. Registration failure/unregistration only log; unregistration does not clear saved endpoint here.

Important doc correction: `docs/unified_push.md` repeatedly describes blocking `wait=true`; actual current source passes **false** and retries. Also source does not share `serializedSync.ts`/`backupCoordinator.ts`/JS background-job state. Swift intent actor and Android load/auth locks are local coordination, not proof that UI, sync, restore, push and backup cannot overlap. In native rewrite, route all wallet owners through one explicit lifetime/operation coordinator and retain necessary parallel receive waiting without holding an exclusive lock indefinitely.

### Exact auth sequence

1. GET getk1. Server issues 32 random bytes as 64 lowercase hex characters, then `_` plus Unix-seconds timestamp; Redis TTL is 600 seconds. Treat the **entire string** as the signing message.
2. Derive Bark keypair from mnemonic, current network variant, **index 0** using `deriveKeypairFromMnemonic`. Sign the challenge using the same native `signMesssageWithMnemonic` implementation. The wrapper's triple-s spelling is real. Server verification uses the Bitcoin Signed Message hash and secp256k1 ECDSA signature parsed by Rust `Signature::from_str`, not raw SHA256(k1), not a JWT signed by the client. Exact derivation is delegated to the Ark SDK; do not invent a new BIP32 path from this inventory.
3. POST login with public key, signature, challenge. Server validates challenge syntax, **atomically consumes it via Redis GETDEL before age/signature validation**, rejects missing/replayed/older-than-600s challenge, verifies signature and mints an HS256 JWT (`sub`=public key, `iat`, `exp`). Invalid signature still consumes a well-formed issued challenge. Server uses 30s JWT expiry leeway; configurable TTL defaults to 72h.
4. Store token securely under `com.noah.auth-token.${APP_VARIANT}` with username `noah`; mnemonic is separate service `com.noah.mnemonic.${APP_VARIANT}`. JWT has in-memory cache too. No refresh token. Refresh is another challenge login; client refreshes when remaining lifetime ≤3h +60s. Concurrent normal logins share one in-flight promise.
5. Send `Authorization: Bearer ...`. On structured `AUTH_REQUIRED`, `INVALID_TOKEN`, or `TOKEN_EXPIRED`, clear token, log in, retry **once**. Other errors do not trigger generic reauthentication. Explicit restore tokens disable retry and never overwrite the installed wallet's token.
6. Push `notification_k1` and `notification_id` are **correlation**, not bearer credentials or reusable login k1. Preserve payload names.

Sources: [`api.ts:153`](/client/src/lib/api.ts:153), [`crypto.ts`](/client/src/lib/crypto.ts), [`walletApi.ts:450`](/client/src/lib/walletApi.ts:450), [`public_api_v0.rs:221`](/server/src/routes/public_api_v0.rs:221), [`k1_store.rs`](/server/src/cache/k1_store.rs), [`utils.rs:8`](/server/src/utils.rs:8), [`auth.rs`](/server/src/auth.rs), [`config.rs:183`](/server/src/config.rs:183). Background localization: [`backgroundTranslations.ts`](/client/src/lib/backgroundTranslations.ts) resolves persisted `getLocale()` with `getMessagesInternal`, independent of GTProvider. App-selected locale controls Bitcoin/fiat formatting independently of device locale; preserve NBSP and BIP177 prefix behavior.
