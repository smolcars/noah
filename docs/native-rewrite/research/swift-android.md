**TL;DR — 2026-10-19.** Yes: shared Swift business logic can run inside a Kotlin Android app. The official SDK now has releases, and shipped apps demonstrate feasibility. For Noah, however, I recommend **a small Rust `noah-core` plus thin Swift/Kotlin platform layers**. Noah already needs Rust and generated bindings; adding Swift to Android introduces another runtime, bridge and build pipeline without preserving an existing Swift core—the current core is TypeScript. Swift-on-Android deserves a bounded prototype if Swift ownership is a strong preference, but should not be the rewrite’s default dependency.

**Evidence — sources accessed 2026-10-19**

1. **SDK status and compatibility.** The [2025-10-24 announcement](https://www.swift.org/blog/nightly-swift-sdk-for-android/) introduced nightly previews; [Swift 6.3, released 2026-03-24](https://www.swift.org/blog/swift-6.3-released/), delivered the first official Android release. The [current installation guide](https://www.swift.org/documentation/articles/swift-sdk-for-android-getting-started.html) specifies **Swift 6.4.1**, an exactly matching host toolchain/SDK, and **NDK r30 LTS**, with macOS/Linux cross-compilation. [Workgroup CI documentation, 2026-03-03](https://forums.swift.org/t/the-current-state-and-future-of-android-testing-on-the-ci/85111), identifies shipped AArch64, x86_64 and ARMv7 targets: Android `arm64-v8a`, `x86_64`, `armeabi-v7a`. This is official Swift-project support; I did not establish an Android Tier-1 designation or commercial support SLA.

2. **Libraries and concurrency.** Foundation, FoundationEssentials, Dispatch and Swift async/await are available. URLSession comes through FoundationNetworking; [an Android developer’s 2026-06-05 networking report](https://forums.swift.org/t/swift-okhttp-swift-bindings-for-okhttp-on-android-java/87128) also describes using OkHttp through swift-java. Availability does not imply Apple-framework parity. In particular, Android’s UI Looper needs integration with Swift’s main executor: [issue #89711, opened 2026-06-05 and still open](https://github.com/swiftlang/swift/issues/89711), reproduces working detached tasks but stalled MainActor/main-Dispatch work in a JNI-hosted app. Keep shared services independent of MainActor and dispatch UI updates through Kotlin.

3. **Size and startup.** A [2026-10-15 first-hand measurement](https://forums.swift.org/t/whats-in-the-34-mb-of-icu-data-in-lib-foundationicu-so-and-what-can-be-removed/90098) using Swift 6.4.1/NDK r30 reports stripped, arm64 reference APKs: **11.2 MB stdlib-only; 17.7 MB FoundationEssentials; 65.7 MB Foundation; 69.2 MB with FoundationNetworking**. Within the Foundation case: ICU **40 MB**, libswiftCore **6.9 MB**, FoundationEssentials **6.2 MB**, Foundation **6.1 MB**. These are one author’s reference APK measurements, not Noah’s incremental cost or Play-download size. ABI splitting avoids delivering every architecture, but does not remove runtime dependencies. I found no defensible current startup-cost benchmark; measure cold launch and first wallet operation on real devices.

4. **Kotlin interoperability.** [swift-java](https://github.com/swiftlang/swift-java) generates Java wrappers plus Swift JNI entry points using `jextract --mode jni`; Kotlin calls the Java API. `wrap-java` generates Swift projections of JVM APIs, including suitably exposed Kotlin APIs. Android uses JNI, not desktop Java FFM. The project warns that pre-1.0 APIs can change. [Current mapping documentation](https://docs.swift.org/latest/documentation/swiftjavadocumentation/featuresjextract/) supports async → CompletableFuture, structs/classes → wrappers with managed native lifetimes, and associated-value enums → generated accessors. These are not automatic Kotlin data classes or suspend APIs. Kotlin can [await CompletionStage](https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-core/kotlinx.coroutines.future/await.html); cancellation reaching the underlying Swift task remains unverified.

5. **Tooling and shipped applications.** An [official Gradle example](https://github.com/swiftlang/swift-android-examples/blob/main/hello-swift-java/hashing-lib/build.gradle) invokes SwiftPM and packages generated bindings/native libraries. [GitHub Actions integration](https://github.com/skiptools/swift-android-action) supports builds and emulator tests. There is no representative Noah build-time estimate: budget for Rust, Swift and Gradle, multiplied across ABIs. [Debugging status, updated 2026-03-24](https://forums.swift.org/t/swift-debugging-on-android-current-state/84155), reports CLI/VS Code progress; seamless mixed Kotlin/Swift Android Studio debugging is unverified. [Sentry’s Android plugin](https://github.com/getsentry/sentry-android-gradle-plugin) uploads native debug files, but Swift frame/async-stack symbolication needs a deliberate release-crash test.

   [Swift’s workgroup, 2025-12-18](https://www.swift.org/blog/exploring-the-swift-sdk-for-android/), names Spark, flowkey, MediQuo and Naturitas as production Swift Android apps, historically using custom interop. [Skip’s 2026-03-26 announcement](https://skip.dev/blog/swift-63-android-support/) confirms native **Skip Fuse** Showcase shipping with official Swift 6.3. Fuse compiles Swift and generates JNI; Skip Lite transpiles Swift to Kotlin. [SCADE AppLogic’s April 2026 documentation](https://www.scade.io/docs) offers Swift-library/AAR integration. Both add vendor tooling; neither removes Noah’s Rust integration work. I did not verify a named production wallet using this complete stack.

**The Bark complication — concrete source inspection**

Inspected `smolcars/bark-bolt-ffi` commit **bbe22f3**, dated **2026-10-19**, and BoltFFI **v0.31.1**:

- [Package.swift](https://github.com/smolcars/bark-bolt-ffi/blob/bbe22f342debc8ae20cb8c42d250b5ae56f4855b/Package.swift) unconditionally depends on an Apple XCFramework. It cannot be consumed unchanged for Android. [boltffi.toml](https://github.com/smolcars/bark-bolt-ffi/blob/bbe22f342debc8ae20cb8c42d250b5ae56f4855b/boltffi.toml) configures Swift under Apple and Kotlin under Android, with three ABIs and minSdk 24.
- [Generated Swift](https://github.com/smolcars/bark-bolt-ffi/tree/bbe22f342debc8ae20cb8c42d250b5ae56f4855b/sdk/swift) imports Foundation and a C module; its modulemap/header, handles and async continuations look portable by inspection. Android needs an alternate SwiftPM C target, matching generated headers and Android libraries. Its Foundation import also makes the larger runtime footprint relevant. **No Android compilation of these Swift bindings was performed.**
- Crucially, [BoltFFI’s Android linker](https://github.com/boltffi/boltffi/blob/v0.31.1/boltffi_cli/src/pack/android/link.rs) exports both `Java_*` and `boltffi_*`. Therefore a plausible arrangement is **Kotlin → JNI → Swift → C ABI → the same Rust `.so`**. Swift need not call Kotlin’s Bark wrapper. Two Rust copies are avoidable: link dynamically to one Bark library; separately embedding its static archive in Swift while retaining the AAR would duplicate it. Verify exported symbols, loading, ownership and NDK compatibility in a prototype.
- [Bark’s runtime](https://github.com/smolcars/bark-bolt-ffi/blob/bbe22f342debc8ae20cb8c42d250b5ae56f4855b/src/ffi/runtime.rs) explicitly lets submitted work continue after foreign cancellation. Cancelling a coroutine/Swift wait must never be interpreted as cancelling a payment.

**Risk comparison — architectural judgment**

| Option | Benefit | Noah-specific cost/risk | Verdict |
|---|---|---|---|
| Swift on Android | One Swift implementation; native execution | Swift runtime/ICU, JNI mapping, Android Bark packaging, debugging | Feasible; prototype first |
| Kotlin Multiplatform | Established shared-logic approach; Swift-friendly SKIE bridge | Additional iOS runtime and Rust adapter; current Bark Kotlin output is JVM-specific | Viable, less direct here |
| Rust + BoltFFI | Reuses required SDK boundary and native toolchains | Rust expertise; careful ownership, cancellation and API design | Preferred for substantial domain rules |
| Write twice | Simplest builds; natural platform APIs | Behavioral divergence in parsers/payment policy | Preferred for thin adapters |

[SKIE](https://skie.touchlab.co/features/) improves suspend/Flow, enums and cancellation on iOS. But [BoltFFI v0.31.1](https://github.com/boltffi/boltffi/blob/v0.31.1/README.md) explicitly limits experimental KMP to JVM/Android, with no Kotlin/Native iOS support. KMP would need an injected platform wallet interface or additional C interop; the existing AAR is not a shared iOS dependency.

**Concrete Noah boundary**

Read-only inspection found **8,567 lines** across `client/src/lib/*.ts`, including adapters and presentation—not 8,567 lines of reusable domain logic.

- **Share first:** parsing/network/amount rules from `sendUtils.ts` (328 lines), rail decisions from `sendFlow.ts` (166), `receiveRequest.ts`, and policy/state transitions from `recurringSchedule.ts` (428). Preserve BIP21/BIP321, BOLT11/BOLT12 and Lightning-address behavior; delegate authoritative wallet validation to Bark. Specify timezone/DST/month-end semantics explicitly. Share monetary conversion/rounding, not localized strings.
- **Extract selectively:** generation/deduplication/retry rules in `backupCoordinator.ts` (199), manifest/restore validation in `backupService.ts` (559), ordering in `serializedSync.ts` (73), and authentication/error policy from `api.ts` (577). Keep actual HTTP/background transfers and secure credential storage behind platform adapters.
- **Other useful domain candidates:** LNURL authentication rules from `lnurlAuth.ts`, repeat-payment metadata from `repeatPayment.ts`, transaction interpretation from `transactionHistory.ts`/`barkMovement.ts`, and fee-review rules from `exitFeeEstimate.ts`; exclude their localized labels. Avoid porting rules already implemented authoritatively in Bark.
- **Keep native:** `pushNotifications.ts`, `tasks.ts`, `recurringBackgroundTask.ts`, permissions, Keychain/Keystore, filesystem lifecycle, timers/wake scheduling, UI/store updates and localized fiat formatting. `sync.ts` is only 39 lines; `walletApi.ts`/`paymentsApi.ts` largely wrap existing SDK operations. Do not recreate those wrappers wholesale in a shared framework.

Start `noah-core` with pure parsers and recurring-policy tests, using shared fixtures in both apps. Keep Noah product policy outside generic Bark; expose it through a coordinated BoltFFI facade, packaging Bark only once. Expand into stateful orchestration only when duplicated behavior warrants it. This recommendation is source-based; Android Swift/Bark compilation, measured startup/build times and complete crash symbolication remain unverified.
