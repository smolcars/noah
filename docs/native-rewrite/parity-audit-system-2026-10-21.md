## Needs decisions (no protected logic changed)

1. **D1 — non-GMS invoice-request claim fallback (Android).** RN `client/nitromodules/noah-tools/android/src/main/java/com/margelo/nitro/noahtools/NoahPushService.kt:499` starts up to 30 nonwaiting single-hash claim attempts, 800 ms apart, after invoice submission; successful claim posts a local receipt. Native `apps/android/app/src/main/java/com/noahwallet/services/push/PushJobs.kt:54` submits the invoice and ends; no bounded claim poll or receipt is attached to that request. `server/src/mailbox_worker.rs:755` uses **send_expo_push_notification**, and `server/src/push.rs:386` excludes UnifiedPush tokens from that path. SDK daemon/periodic/foreground work may eventually claim, but that does not establish the same prompt receipt/latency. **Proposed:** decide between a dedicated, independently budgeted UnifiedPush claim wait with durable duplicate-safe receipt evidence, or server UnifiedPush claim delivery. Keep existing session gates/settlement and do not simply append an unbounded wait to invoice work. This sweep did not exercise a real distributor.
2. **D2 — foreground widget expiry/cadence (both).** RN `client/src/hooks/useWidget.ts:29` reacts to Home balance data and always calculates VTXO expiry. Native `apps/ios/Noah/Features/Recurring/RecurringLive.swift:38` and `apps/android/app/src/main/java/com/noahwallet/recurring/RecurringRuntime.kt:40` publish balance with nil expiry from recurring refresh callbacks, including ordinary foreground ticks; `apps/ios/Noah/Services/Push/WidgetDataWriter.swift:15` / `apps/android/app/src/main/java/com/noahwallet/services/push/WidgetDataWriter.kt:20` turn nil into -999, hiding expiry despite extant VTXOs. Home summary refresh itself has no widget writer (`AppModel.swift:250`, `AppModel.kt:310`), so balance changes can wait for that recurring/minute pass. This sweep restores complete post-recurring-push refresh on Android (iOS already has it). **Proposed:** a full-summary+expiry widget publication triggered by admitted foreground balance refresh, with stage checks after both reads, independent from payment settlement. Decide its lifetime/budget before adding extra wallet reads to recurring execution callbacks.
3. **D3 — manual 24-word recovery entry (both).** RN `client/src/screens/RestoreWalletScreen.tsx:35` passes any nonempty trimmed phrase to restore; backup authentication/decryption/native loading do not enforce a screen-level 12-word limit (`client/src/lib/backupService.ts:374`). Native restore fields and validators require 12 exactly (`apps/ios/Noah/Features/Onboarding/RecoveryPhraseInput.swift:10`; `apps/android/app/src/main/java/com/noahwallet/ui/RecoveryPhraseInput.kt:9`); Android stored-seed admission explicitly permits 12 **or 24** (`apps/android/app/src/main/java/com/noahwallet/services/storage/StoredMnemonic.kt:18`). **Proposed:** confirm support for valid 24-word RN/imported-wallet backups; if supported, add a 12/24 presentation mode/paste contract and negative checksum/count tests without changing restore transaction ordering. Source comparison establishes the input restriction; no 24-word backup was restored in this sweep.
